# Course Project

## Purpose

Select one software system to design from idea to full engineering specification.

## What success looks like

A strong project is coherent and easy to review:

- the product promise, goals, and requirements agree;
- estimates create a clear design pressure or show that a simple design is
sufficient;
- every major component has a stated responsibility and reason to exist;
- diagrams and written responsibilities describe the same design;
- one clear system of record settles each important fact;
- important reads and writes have visible success and failure results;
- retries, timeouts, dependency failures, and process failures have defined  
outcomes;



## Project and Labs

The two work streams have different purposes:


| Work           | System                        | Purpose                                                  |
| -------------- | ----------------------------- | -------------------------------------------------------- |
| Shared Labs    | Personal Investment Dashboard | Apply one method to a common problem and compare answers |
| Course project | Student-selected system       | Transfer selected methods to a different domain          |


Complete each shared Lab first. Update the course project only at the stated
checkpoints. The project does not repeat every Lab task.

## Working document

- Keep one cumulative document.
- Write each diagram as a Mermaid block and keep its source in the document.
- Keep names, directions, records, and responsibilities consistent across all
sections.
- State assumptions and unresolved questions. Do not hide uncertainty.
- Cite external facts, benchmarks, product behavior, and diagrams that came  
from another source.

## Propose two candidates

Submit two short project candidates before the first Lab. Do not select an
architecture or technology at this stage.

An appropriate candidate has:

- one clear main stakeholder and useful result;
- two to four actors or external systems;
- a scope that can be described with five functional requirements;
- one important read;
- one state-changing flow;
- persistent data;
- a realistic timeout, dependency, or process-failure case;

Avoid a complete social network, cloud platform, payment network, search engine, or exchange. These domains are too broad unless one small workflow is selected.
